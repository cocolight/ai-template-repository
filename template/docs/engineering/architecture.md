# 架构与代码约定

> 项目：{{PROJECT_NAME}}。本文件说明「代码怎么组织」；
> 「什么时候算完成」见 [definition-of-done.md](definition-of-done.md)。

## 1. 目录结构

- `src/` — 源码（入口与业务逻辑）
- `tests/` — 测试
- `docs/` — 项目文档（使用指南、参考等）
- `docs/engineering/` — 工程协作文档：架构 / 配置 / 完成定义 / 发版 / ADR
- `scripts/` — 辅助脚本

（按技术栈补充更细的分层，例如 `src/<pkg>/` 或 `src/domain|infra|ui/`。）

## 2. 分层与依赖方向

- 依赖方向单向：入口 → 业务逻辑 → 基础设施；底层不得反向依赖上层。
- 纯逻辑与 I/O 分离，便于单元测试（参考示例中把纯函数抽出的做法）。
- 搭建时把分层 / 依赖方向做成可检查的门禁（按技术栈选型实现，接入 CI），让违规在 PR 阶段暴露。
- 可抄样板在模板仓库的 example 示例目录：分层合同与 CI 步骤齐备，按所用技术栈对照抄写。

## 3. 错误处理

- 不吞异常 / 错误；错误信息须包含足够定位上下文。
- （补充本项目的统一策略：错误如何表示、如何向上传播、如何呈现给用户。）

## 4. 日志

- 使用统一日志入口与级别（debug / info / warn / error）；禁止用裸打印做长期日志。
- 日志中不得输出密钥或个人信息。

## 5. 依赖引入规则

- 新增依赖前先确认标准库无法满足；优先轻量、维护活跃的库。
- 新增依赖须在提交 / PR 说明理由，避免为小功能引入重依赖。
- 每个直接依赖须在 `../../THIRD-PARTY.md` 登记许可证（SPDX 标识）、用途与是否随分发，作为合规审计的单一事实源。
- 依赖漏洞告警与版本升级的开关、响应约定见 `configuration.md` §5；评估漏洞影响时查 `../../THIRD-PARTY.md` 的「是否随分发」列。

## 6. 密钥管理

- 密钥 / token / 私钥一律用环境变量或仓库外文件；`.env` 不入库。
- 提供 `.env.example` 作为占位示例。

## 7. 腐化信号与重构触发

出现下列任一信号，视为腐化开始：先评估重构；确不重构的，记一条 ADR 写明理由。

- 出现跨层调用 / 反向依赖（违反 §2）
- 同一逻辑出现在三处及以上
- 函数或文件长到职责边界模糊（需要滚动才能看清它管什么）
- 测试与实现脱节：测试失败已无法定位问题

重构走正常工作流（ROADMAP 立项或随 bugfix 进行），不单开流程。
